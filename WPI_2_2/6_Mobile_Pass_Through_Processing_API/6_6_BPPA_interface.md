## 6.6 BPPA Interface

The BPPA authentication method is mTLS. Following parameters will be required for access:

- Private key
- Client certificate
- Certificate Authority (CA) root certificate
- Certificate Authority intermediate certificates

**CSR Requirements**

- Environment subdomain must be included.
- RSA key length: minimum **4096-bit**
- Recommended TTL: **3 years**
- Default TTL: **1 year**
- Maximum TTL: **10 years**

### 6.6.1 PTP Transaction Data

PTP transaction data can be obtained using the BPPA transaction data collection endpoint.

The `ptp_token` must be provided in the request. The token is returned in the MPPA response by the ToM application.

#### 6.6.1.1 Endpoint

```http
POST /bppa/v1/ptp-data/collect
```

#### 6.6.1.2 Request

| Field | Location | Mandatory | Type | Description |
|---------|----------|----------|---------|-------------|
| ptp_token | Body | Yes | String (JWT) | PTP token |

#### 6.6.1.3 Processing Rules

- The `ptp_token` must be validated by vpos-main.
- If valid, `transaction_id` and `merchant_id` are extracted from the token.
- Response payload is built using the transaction ID from the token.
- No data is returned for expired tokens.
- After successful response delivery, transaction status changes to `PTP_COLLECTED`.
- Responses are allowed for transactions in statuses:
  - `PTP_READ`
  - `PIN_REQUESTED`
  - `PTP_COLLECTED`

#### 6.6.1.4 Response

| Code | Description |
|--------|-------------|
| 201 | OK - `PTPTransactionData` |
| 4XX / 5XX | HTTP error - `ProblemDetails` |

---

### 6.6.2 PTPTransactionData

| Field | Mandatory | Type | Description |
|---------|-----------|------|-------------|
| id_transaction | Yes | UUID | Transaction ID |
| mid | Yes | String | Merchant MID |
| id_merchant | Yes | UUID | Merchant ID |
| ptp_cryptogram | Yes | Base64 String | Encrypted payload |
| cryptogram_recipient | Yes | String | Cryptogram recipient name |
| cryptogram_valid_date | Yes | String (date-time) | Cryptogram validity date |
| encrypted_pinblock | No | Base64 String | Encrypted PIN block, available only when PIN was collected |
| pinblock_format | No | String | `isoFormat0`, `isoFormat1`, `isoFormat2`, `isoFormat3`, `isoFormat4` |
| ksn | No | String | Key Serial Number |

---

### 6.6.3 ProblemDetails

Problem Details extended with additional fields:

- `code`
- `error_code`
- `additionalInfo`

#### 6.6.3.1 Structure

| Field | Mandatory | Type | Description |
|---------|-----------|------|-------------|
| detail | Yes | String | Human-readable explanation of the problem |
| status | Yes | Integer | HTTP status code generated by server |
| instance | Yes | URI | URI identifying the specific occurrence |
| title | Yes | String | Short summary of problem type |
| type | Yes | URI | URI identifying problem type |
| code | No | String | SoftPOS error code (deprecated, backward compatibility) |
| additionalInfo | No | String | Additional error-related information |
| error_code | No | String | SoftPOS error code |

---

### 6.6.4 Encrypted Payload

Transaction payload is created based on acquirer configuration (`trrd:tags`).

Payload format: **TLV**

#### 6.6.4.1 Example Unencrypted Payload

```text
57 13 49 40 36 27 07 63 88 04 D2 51 12 01 17 06 43 83 00 00 0F 5F 34 01 00
```

#### 6.6.4.2 Encryption Process

1. Payload is built in TLV format.
2. Payload is sent to Cryptohub.
3. Cryptohub encrypts sensitive transaction data.
4. Encrypted payload is Base64 encoded.
5. Cryptogram recipient name is included in the response.
6. Both values are returned in `PTPTransactionData`.
